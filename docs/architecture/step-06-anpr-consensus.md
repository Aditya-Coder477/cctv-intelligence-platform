# Step 6 Architecture -- ANPR / OCR & Multi-Frame Consensus Engine

## Overview

Step 6 consumes license-plate candidate crops generated by Step 5 (`data/detections/<camera_id>/plate_candidates.jsonl`) and determines the vehicle registration number.

> **Core Philosophy**: No single OCR reading is trusted as ground truth. Final registration numbers are declared ONLY when supported by multi-observation cross-frame consensus.

---

## Technical Pipeline

```
Step 5 Plate Candidates (plate_candidates.jsonl)
                       |
                       v
         Candidate Eligibility Evaluator
   (filters MISSING_CROP, TOO_SMALL, LOW_QUALITY, etc.)
                       |
                       v
         OCR Preprocessing Cascade
    (original -> grayscale -> upscaled -> contrast -> sharpened)
                       |
                       v
              Text Normalization & Audit
       (strip special chars, IND prefix, uppercase, log char swaps)
                       |
                       v
           Indian Plate Format Validation
       (Standard 10, Short/Legacy, Bharat BH patterns)
                       |
                       v
               Evidence Scoring
    (OCR confidence, format boost, plate quality, det conf)
                       |
                       v
         Multi-Frame & Cross-Variant Consensus
      (frame-level diversity vs variant grouping +
        fuzzy edit-distance clustering + PTS tracking)
                       |
                       v
             Recognition Status Assignment
    (CONFIRMED, PROBABLE, UNCERTAIN, UNREADABLE)
                       |
                       v
            Structured Outputs & Evidence Chain
     (raw_observations.jsonl + anpr_consensus.json)
```

---

## 1. Modular OCR Engine Abstraction

The OCR subsystem adheres to the `OCRRecognizer` interface:
- **`EasyOCREngine`**: Primary PyTorch-based engine (`easyocr` 1.7.2) tuned for alphanumeric license plate recognition (`allowlist='ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789'`). Features automatic canvas pre-scaling and padding for small crops.
- **`OpenCVContourOCREngine`**: Built-in zero-dependency fallback engine using character contour segmentation. Guarantees 100% offline functionality without external network access or pre-trained neural weights.
- **`OCREngineFacade`**: Auto-selects EasyOCR by default, falling back to OpenCV contour detection only if explicitly requested.

---

## 2. Text Normalization & Correction Audit

`normalize_with_audit()` converts text to uppercase, strips non-alphanumeric characters, strips leading `IND` country badge prefixes, and tracks ambiguous character mappings ($O \leftrightarrow 0, I \leftrightarrow 1, B \leftrightarrow 8, S \leftrightarrow 5, 6 \leftrightarrow G$) based on positional rules (e.g. State Code positions $0,1$ vs Serial Number positions $6 \dots 9$).

Raw OCR readings are **never** silently overwritten; every correction is logged with `original_char`, `corrected_char`, `position`, and `reason`.

---

## 3. Indian Registration Plate Validation

`validate_indian_plate()` checks normalized strings against three official Indian registration formats:

1. **Standard 10-char Format**: `State(2) + District(2) + Series(2-3) + Number(4)` e.g., `GJ01AB1234`.
2. **Short / Legacy Format**: `State(2) + District(1-2) + Series(1) + Number(1-4)` e.g., `GJ05A1234`.
3. **Bharat Series (BH)**: `Year(2) + BH + Number(4) + Series(1-2)` e.g., `22BH1234AA`.

Partial or incomplete strings (e.g. `GJ01AB12`) return `is_valid=False`. Missing characters are **never** hallucinated to force regex matches.

---

## 4. Multi-Frame vs Cross-Variant Consensus Rules

To prevent skewed voting:
- **Preprocessing Diversity**: Multiple OCR runs on different variants (grayscale, upscaled, contrast) of the *same* video frame (`frame_id`) are grouped into a single frame-level vote (taking the maximum observation score).
- **Physical Frame Diversity**: Genuinely distinct video frames (different `frame_id` / PTS timestamps) contribute independent physical evidence votes.
- **Fuzzy Clustering**: Levenshtein edit-distance clustering ($\le 1$) merges minor character disagreements (e.g. `GJ01AB1234` vs `GJ01A81234`), accumulating support towards the stronger candidate string.

---

## 5. Recognition Status Assignment

| Status | Conditions |
|---|---|
| **`CONFIRMED`** | Weighted score $\ge 0.70$, $\ge 2$ distinct physical video frames, valid Indian plate format. |
| **`PROBABLE`** | Weighted score $\ge 0.50$, $\ge 1$ frame, valid Indian plate format. |
| **`UNCERTAIN`** | Low confidence or conflicting candidate readings. `final_registration_number = null`. |
| **`UNREADABLE`** | No readable text extracted from any candidate frame. `final_registration_number = null`. |

## 7. Current ANPR Evaluation Status & Benchmarks

### Preliminary vs Rigorous Benchmark Status
- **Initial 8-Sample Sanity Check**: Showed 75% normalized exact-match accuracy. As documented in the sample size policy, this was strictly a preliminary debugging test and must **never** be cited as final ANPR performance.
- **Development Benchmark (36 samples)**:
  - Total records: 36 (20 real Sentinel crops from `cam01` + 16 controlled calibration samples).
  - Controlled samples normalized accuracy: **43.8%** (7/16).
  - Real Sentinel crops: **0.0%** (20/20 unreadable/uncertain).
  - Primary Root Causes: Real Sentinel crops from `cam01` overhead camera are only $20\text{--}35\text{px}$ wide (`PLATE_TOO_SMALL`: 16 samples, `BLUR`: 5 samples, `GLARE`: 2 samples).
- **Held-Out Benchmark (10 samples)**:
  - Reserved strictly for unbiased evaluation without parameter tuning.
  - Normalized exact-match accuracy: **70.0%** (7/10).
  - Character accuracy: **85.0%**.

### Preprocessing Ablation Findings
| Variant | Normalized Exact Match (%) | Avg Character Accuracy (%) |
|---|---|---|
| `original` | 19.4% | 34.7% |
| `grayscale` | 19.4% | 34.7% |
| `upscaled` | 19.4% | 35.6% |
| `contrast` (CLAHE) | **25.0%** | **38.1%** |
| `sharpened` | 16.7% | 35.0% |

*Conclusion*: Contrast enhancement via CLAHE (`contrast`) provides the highest gain (+5.6% exact match) for low-light and low-contrast license plates.

### Sample Size Policy
- **8 samples**: Preliminary debugging only.
- **30–50 samples**: Useful development and ablation benchmark.
- **100+ samples**: Stronger final operational evaluation across multiple camera angles.

## 8. Architectural Boundary

> [!IMPORTANT]
> Step 6 ends at **"What registration number is visible on the license plate?"**
>
> It does **NOT** perform watchlist matching, alert generation, Kafka publishing, or PostGIS spatial queries.
> Those operations belong to Step 7 (Observation Storage), Step 8 (Watchlists), and Step 9 (Alerting).
